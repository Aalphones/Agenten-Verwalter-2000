Anmerkungen am Code
Thema

Neu in diesem Stand

  • Eine Seite je Phase, ohne Unterseiten: Ergebnis, Weg (eingeklappt), Review mit offenen Befunden und Schaubild, dann alle Stopps als Abschnitte. Links auf einen Stopp springen an seine Stelle.
  • Zwei schlanke Werkzeuge für alle Stationen: note(text, at?, kind?, resolves?) und figure(caption, mermaid | image, marks?, at?). Phase und Rolle kennt der Verwalter; ohne at gilt der letzte Edit.
  • Ablage als Markdown je Phase: Jeder Aufruf hängt einen Eintrag an die Rohfassung. Haiku gibt die geordnete Fassung zurück: Ergebnis, Weg, Titel und Reihenfolge, die Einträge nur als IDs. „Werkzeuge zeigen“ blendet beide am Ende jeder Phase ein.
  • Der Verwalter prüft, dass jede ID genau einmal vorkommt; sonst gilt die Reihenfolge der Rohfassung.
  • Prüfung je Phase, ohne Tokens: Prüfkette, Tests, Abdeckung der neuen Zeilen und Mutation liest der Verwalter aus den Berichtsdateien der Läufe (JUnit-XML, LCOV, Mutations-JSON). Im Code markiert: neue Zeilen ohne Test (gelber Rand) und überlebte Mutanten als Anmerkung „M“ (Beispiel: Phase 2 · Sperre). Keine Ampel-Schwellen; rot nur bei fehlgeschlagenen Tests.
  • Vorher im Code: Entfernte Zeilen kommen aus Git und stehen rot zwischen den neuen, mit alter Zeilennummer; Läufe über sechs Zeilen sind eingeklappt (Beispiel: Phase 2 · Sperre).
  • Vorher im Schaubild: Der Agent setzt im Mermaid-Text „+ “, „- “ oder „~ “ vor Zeilen. Daraus zeigt der Bericht Unterschied, Vorher und Nachher — ein Schaubild, keine zwei (Phase 2 · Review, Phase 2 · Grenze, Phase 3 · Range).

Aufgabe

  • Prüfen, was eine Umsetzung geändert hat, und dabei am echten Code bleiben. Lesen ist kein Pflichtprogramm: keine Häkchen, kein Fortschritt.

Woher eine Anmerkung kommt

  • Gratis: Diff und Zeilen aus Git · Ergebnis aus Commit bzw. „Station fertig“ · Zweckzeile, die der Agent ohnehin vor einer Folge von Edits schreibt, am Code dieser Edits · Bilder, die die Station ohnehin anlegt.
  • note (direkt nach dem Edit bzw. beim Prüfen): { text, at?, kind?, resolves? } · figure: { caption, mermaid | image, marks?, at? }. Jeder Aufruf hängt einen Markdown-Eintrag an die Rohfassung der Phase und gibt nur seine ID zurück.
  • Ohne at nimmt der Verwalter Datei und Zeilen aus dem letzten Edit der Session und hält sie beim Commit gegen Git nach; trifft er nicht, bekommt der Agent sofort einen Fehler.
  • Kommentare von dir kommen als Review-Kommentare mit Datei und Zeile beim Agenten an. Abnehmen kann nur du.

Offene Punkte

  • Session ohne Umsetzung (privat direkt im Chat): Bericht je Session im selben Reiter?
  • Wandert eine Anmerkung mit, wenn eine spätere Phase dieselbe Zeile ändert, oder bleibt sie am alten Stand?
  • Zweckzeilen am Hunk: erkennt der Verwalter die Zuordnung Edit → Zeilen sicher genug, oder braucht es einen Probelauf an echten Sessions?
  • Mermaid ist noch keine Abhängigkeit der Oberfläche.
