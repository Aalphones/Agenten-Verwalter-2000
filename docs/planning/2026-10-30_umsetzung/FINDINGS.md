# FINDINGS

Append-only. Jeder Eintrag mit Ziel-Tag; die Ziel-Phase hakt ab, was sie eingearbeitet hat. Über das Projekt hinaus tragende Fehler mit `→ Vault: <Entity> — Symptom · Ursache · Fix` (hebt `session-review` in den Vault).

Format: `- [ ] → Phase N: <Erkenntnis, 1–3 Zeilen — was wurde entdeckt, was heißt das für die Ziel-Phase>`

- [x] → Phase 2: `stationState.ts` hat in Phase 1 nur `stateLabel` und `stateIcon` (Zustand → Symbol der Sessions); `URGENCY_ORDER` entfiel, weil der Core `urgency` liefert. `stateColorClass` und `implementationOrder.ts` legt Phase 2 an, wenn Zeitleiste und Kartei sie brauchen.
- [x] → Phase 2: Die Übersicht des Vorhabens (`ProjectOverview`, Kopfzeile „N Sessions“) bekommt über `sessionsOf` weiter **alle** Sessions samt Stationen; nur die Sidebar filtert mit `visibleSessions`. Entscheiden, ob die Übersicht Stationen als Karten zeigt oder ausblendet.
- [x] → Phase 3: `SessionState.station_of` wird beim App-Start (`restore`, auch beim Wiederherstellen aus dem Archiv) aus der Datenbank gesetzt; beim Start einer Station muss Phase 3 es selbst setzen, sonst zeigt die Sidebar die neue Station als Session-Zeile und `useImplementations` lädt bei ihren `session://changed` nicht nach.
- [x] → Phase 3: `db::implementations` hat `set_station_session`, `complete_station`, `set_flags` schon; `ImplementationService { countdowns }` ist gemanagt. `build_view` setzt `starts_at` immer `None` und kennt `Countdown` noch nicht — Phase 3 reicht die Countdown-Enden hinein.
- [x] → Phase 4: Eine startbare Station ohne Countdown ist `ready` (nicht `pending`), auch bei Automatik an; `start::schedule_ready(app, id)` plant für alle `ready`-Stationen einen Countdown und läuft schon über Wellen (`schedule::may_start`). Nach `replace_upcoming_phases` und nach „Übernehmen“ `schedule_ready` aufrufen, wenn `auto_start` an ist und `stop_after_current` aus. `implementation::plan_completion` fügt Fix-Runden ein; `db::complete_station_with_followups` verschiebt Positionen — `replace_upcoming_phases` darf nur Phasen ohne gestartete Station anfassen.
- [x] → Phase 4: `replace_upcoming_phases(connection, removed_phase_ids, phases, stations)` löscht und legt neu an, Positionen kommen vom Aufrufer (`implementation::phase_rows(id, inputs, first_position)`). `ChangeView.session_number` kommt aus den Nummern aller Sessions des Vorhabens; eine gelöschte Session ergibt 0.
- [x] → Phase 5: Der Lagebericht führt unter „Jetzt“ zusätzlich Stationen, die auf dich warten („wartet auf dich“) oder einen Fehler haben („Fehler“) — sonst stünden sie nirgends. `report::text` hat keinen Parameter für den Namen des Vorhabens (die Zeilen brauchen ihn nicht); `for_inquiry` ist da. Der Text einer Rückfrage ist ihre erste Zeile.
- [x] → Phase 6: Neue Abhängigkeit `chrono` (nur Feature `clock`, lag schon über andere Crates im `Cargo.lock`, kein neuer Download) für die Ortszeit im Lagebericht — in AGENTS.md/Konventionen erwähnen, falls dort Abhängigkeiten geführt werden. `SessionSummary` hat zwei neue Felder (`stationOf`, `inquiryOf`), Glossar-Begriffe „Umsetzung“, „Station“, „Lagebericht“ fehlen noch.
