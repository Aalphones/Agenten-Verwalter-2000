# Terminal im Vorhaben

Ziel: Jedes Vorhaben bekommt einen Reiter „Terminal“ neben Chat/Changes/Artefakte bzw. Übersicht/Changes/Artefakte. Darin laufen ein oder mehrere echte Terminals (Pseudo-Terminal im Core, xterm.js in der Oberfläche) im Workspace-Ordner des Vorhabens — genau dem Ordner, in dem der Agent arbeitet. Die Shell richtet sich nach dem Betriebssystem: Windows `cmd.exe`, macOS die Login-Shell des Users (Standard `zsh`), Linux die Login-Shell des Users (Standard `bash`). Die Terminals leben im Core, überstehen Reiterwechsel und ein Neuladen der Oberfläche und enden mit dem Archivieren des Vorhabens oder dem Beenden der App. Kein Design-Entwurf vorhanden; gebaut wird nach dem Muster der bestehenden Reiter.

Kontext für jeden Umsetzer: [AGENTS.md](../../AGENTS.md), [docs/code-map.md](../code-map.md) (Zeilen „Vorhaben“, „Sessions“, „Artefakte“, „Generierte Typen“, „Aufruf-Wrapper“, „Fehler am Command-Rand“, „Design-Tokens“), [docs/glossary.md](../glossary.md), [docs/conventions/rust.md](../conventions/rust.md), [docs/conventions/typescript.md](../conventions/typescript.md), [docs/conventions/react.md](../conventions/react.md), [docs/conventions/tailwind.md](../conventions/tailwind.md), [docs/conventions/linting.md](../conventions/linting.md), [docs/conventions/commits.md](../conventions/commits.md), [docs/conventions/releases.md](../conventions/releases.md). ## Festgelegte Entscheidungen

- **Eingebettet, nicht extern:** echtes Pseudo-Terminal im Core über `portable-pty` (Windows: ConPTY, macOS/Linux: Unix-PTY), Anzeige mit xterm.js. Gegen „System-Terminal in eigenem Fenster öffnen“: drei verschiedene Startwege je Betriebssystem und Linux-Terminal-Zoo, und das Terminal läge außerhalb der App, in der der User arbeitet.
- **Shell je Betriebssystem** (`src-tauri/src/terminal/shell.rs`, eine Funktion `shell_command() -> ShellCommand { program: PathBuf, args: Vec<String>, label: String }`):
  - `#[cfg(windows)]`: Programm aus Umgebungsvariable `ComSpec`, sonst `cmd.exe`; keine Argumente; Label `cmd`.
  - `#[cfg(target_os = "macos")]`: Programm aus `SHELL`, sonst `/bin/zsh`; Argument `-l`; Label = Dateiname ohne Pfad (z. B. `zsh`).
  - `#[cfg(all(unix, not(target_os = "macos")))]`: Programm aus `SHELL`, sonst `/bin/bash`; Argument `-l`; Label = Dateiname ohne Pfad.
  - Zusätzlich auf allen Systemen: Umgebungsvariablen `TERM=xterm-256color` und `COLORTERM=truecolor`; Arbeitsordner = Workspace des Vorhabens.
- **Gehört dem Vorhaben, nicht der Session:** Alle Sessions eines Vorhabens teilen den Workspace; der Workspace kommt aus `Session.workspace` einer beliebigen Session des Vorhabens (alle gleich). Der Reiter erscheint in Session-Ansicht und Übersicht und zeigt dieselben Terminals.
- **Mehrere Terminals je Vorhaben, höchstens 8 laufende.** Nummer je Vorhaben ab 1 aufsteigend, nie wiederverwendet bis zum App-Ende. Titel in der Leiste: `<Label> <Nummer>` (z. B. `cmd 1`).
- **Nur im Speicher:** keine Datenbank, keine Migration. Nach einem App-Neustart gibt es keine Terminals mehr (Prozesse enden mit der App).
- **Puffer im Core:** je Terminal die letzten 1 MiB Ausgabe als Text. Beim Öffnen des Reiters schreibt die Oberfläche den Puffer neu in ein frisches xterm — deshalb überstehen Terminals Reiterwechsel und Neuladen. Ein Vollbild-Programm (z. B. `vim`) kann nach einem Wechsel verzerrt erscheinen, bis es neu zeichnet; hingenommen.
- **Ausgabe als UTF-8-Text:** Der Lese-Thread zerlegt Bytes in Text und hebt eine am Blockende abgeschnittene UTF-8-Folge für den nächsten Block auf; ungültige Bytes werden `U+FFFD`.
- **Übertragung:** Ausgabe per `tauri::ipc::Channel` (je Terminal höchstens ein angehängter Kanal; ein neuer ersetzt den alten). Listenänderungen per Ereignis `terminal://changed`.
- **Lebensdauer:** „×“ an einem Terminal beendet den Prozess und entfernt das Terminal. Ein Terminal, dessen Shell von selbst endet (`exit`), bleibt mit seiner Ausgabe und dem Vermerk „beendet“ stehen, bis „×“ es entfernt. Archivieren eines Vorhabens beendet seine Terminals. Beenden der App beendet alle.
- **Erster Besuch:** Öffnet der User den Reiter und das Vorhaben hat kein Terminal, startet automatisch eines.
- **Zwischenablage:** Windows/Linux `Strg+C` kopiert, wenn Text markiert ist, sonst geht `^C` an die Shell; `Strg+V` fügt ein. macOS `Cmd+C`/`Cmd+V`. Einfügen läuft über das native `paste`-Ereignis des Browsers (xterm.js verarbeitet es selbst), nicht über `navigator.clipboard.readText`.

## Kontrakt

```rust
// src-tauri/src/terminal/model.rs — derive(Serialize, Clone, TS), #[serde(rename_all = "camelCase")], #[ts(export)]
pub struct TerminalInfo {
    pub id: String,                 // uuid v4
    pub project_id: String,
    pub number: u32,                // je Vorhaben ab 1
    pub label: String,              // "cmd", "zsh", "bash", …
    pub cwd: String,                // Workspace des Vorhabens
    #[ts(type = "number")] pub started_at: f64, // ms seit Epoche
    pub running: bool,
    pub exit_code: Option<u32>,     // gesetzt, sobald die Shell endete (falls bekannt)
}

#[serde(tag = "kind", rename_all = "camelCase")]
pub enum TerminalOutput {
    Data { text: String },
    Exit { code: Option<u32> },
}

pub struct TerminalChanged { pub project_id: String } // Nutzlast von "terminal://changed"
```

## Finale AK

1. In jeder Session-Ansicht und in jeder Übersicht eines Vorhabens steht der Reiter „Terminal“; laufen Terminals, zeigt er ihre Zahl.
2. Erster Klick auf den Reiter in einem Vorhaben ohne Terminal startet `cmd 1` (Windows) im Workspace des Vorhabens; `cd` gibt den Pfad `…\.verwalter\workspaces\<id>` aus — denselben, den der Agent als Arbeitsordner hat.
3. Auf macOS startet die Login-Shell aus `SHELL` (sonst `/bin/zsh`), auf Linux die aus `SHELL` (sonst `/bin/bash`), jeweils mit `-l` — belegt per Code-Blick auf die `cfg`-Zweige in `terminal/shell.rs`; Laufzeit auf macOS/Linux ist nicht geprüft (wie `linux-pfade`).
4. „+“ öffnet ein weiteres Terminal; ein 9. laufendes wird mit dem Satz aus dem Kontrakt abgelehnt, sichtbar über der Leiste.
5. Wechsel auf Chat und zurück, Wechsel in ein anderes Vorhaben und zurück sowie `Strg+R` (Neuladen) behalten Terminal und Ausgabe.
6. Farben, Umlaute (`echo äöü`), Größenänderung des Fensters (Spaltenzahl folgt, `mode con` zeigt sie) und `Strg+C` bei laufendem `ping -t localhost` funktionieren.
7. Markierter Text wird mit `Strg+C` kopiert, `Strg+V` fügt ein.
8. `exit` lässt das Terminal mit „beendet“ stehen; „×“ entfernt es und beendet einen noch laufenden Prozess.
9. Archivieren des Vorhabens und Beenden der App lassen keinen Shell-Prozess zurück.
10. Hell- und Dunkelmodus: das Terminal übernimmt Hintergrund, Schrift und Cursor aus den Tokens und wechselt mit dem Farbschema.
11. ADR 052, Glossar, Code-Map und AGENTS.md sind nachgezogen; `pnpm check` grün.

## Wackelstellen (Konfidenz)

- 🟡 **Enkelprozesse unter Windows:** ob ein in `cmd` gestartetes `pnpm dev` (node) mit „×“ bzw. App-Ende mitstirbt, hängt am Schließen der ConPTY. Check: im Terminal `ping -t localhost` starten, „×“, dann `Get-Process PING` — leer = gut; sonst Job-Objekt nachrüsten (FINDINGS).
- 🟡 **Letzte Ausgabezeilen unter Windows:** der Warte-Thread schließt die ConPTY nach Prozessende; Text, der noch unterwegs war, kann fehlen. Check: `cmd /c "echo eins & echo zwei & exit"` als Befehl — beide Zeilen müssen stehen.
